# Phase 6.1 — exact evaluation, reference oracle and architectural constraint specification

**Disposition:** CANDIDATE ONLY — not frozen, implemented or executed. The two candidate JSON specifications contain 72 declarative inputs and separately stored expected outcomes; no run fixture generator, selector evaluation, scientific output or test result exists. The author approved design and adversarial review, not execution. This document supersedes ambiguities in the Phase 6 concept only; Study 2, 9 and 10 remain frozen.

## 1. Scope, units and evaluation contract

There are 48 target cases (eight predicates × six case types), 12 derivation cases (two rules × six), and 12 challenge cases. Of these, 64 are source-mapping endpoints, with 23 prespecified admissible and 41 nonadmissible expected cases; eight are **separate ledger diagnostic instances**. These counts describe the design, not measured results. The 17 planned metamorphic checks are paired transformations of base cases, not additional independent evidence or included in the 72 denominator. No pooling with S9/S10, inferential confidence intervals, p-values or real-flight rate. Pre-exposure to the expected baseline and authored synthetic contracts is disclosed. No claim of blinded human coding or general natural-language semantic recognition.

### Exact input and output handling

The input JSON specifies a target (or null for ledger diagnostics), schema descriptors (native-field flag, meaning, authority, visibility, domain and subject/decision/clock/source/evidence scopes), row context and values, requested context, and optional ledger diagnostic input. All are fictional, stipulated authority and verifier outcomes, not real cryptography or attestations. Each case is independent of other cases' decision context. For mapping evaluator, pass only target/schema/record/requested_context, not case ID, family, reference expected outcomes, case-specific diagnostic labels, filenames or ordering. Ledger evaluator receives the declared ledger and requested context, not expected diagnostics. Runner retains an opaque routing key outside evaluator. Distinct lexical field names are not equivalent evidence.

Use four qualification classes DIRECT, DERIVABLE_BY_PREDECLARED_RULE, AMBIGUOUS, ABSENT. Here DIRECT refers to **documented schema capability**, not population-wide validated native coverage. This extension's row admission statuses are ADMIT (literal true or false), UNKNOWN (unqualified/context mismatch), UNKNOWN_MISSING (qualified schema but missing value), REJECT_INVALID (malformed value). Value is null for nonadmission. Visibility null means no relevant evidence role, while offline and documentation-only cases explicitly retain the excluded role. Preserve release_domain flags (DOMAIN_VIOLATION_HOLD / MISSINGNESS_HOLD / NOT_ASSESSED); a capability is not a population claim. The historical S9 UNSW domain-deviation decision remains unchanged.

Qualification precedence: (a) remove nonnative documentation and offline-only truth as qualifying operational input; when no related native operational candidate remains, ABSENT, with the explicit excluded role if present; (b) for related operational fields, evaluate documented meaning, required authority and declared schema context, not field name. A non-equivalent proxy or wrong schema scope is AMBIGUOUS. (c) if direct meaning and authority match, DIRECT; otherwise if a named extension-only rule has all required fields with authoritative documented semantics and common scope, DERIVABLE_BY_PREDECLARED_RULE. (d) row admission: check the row context against requested context (including snapshot, decision time, subject, epoch, clock, source, evidence), then missing input, then exact type/domain, then normalize/derive. Schema-domain and row-domain are not interchangeable. A known negative guard or verifier result is admitted false, not rejected. A stale row under a good schema is DIRECT/UNKNOWN. A missing or malformed row under a derivable schema remains DERIVABLE as capability, not operationally observed. Specific reason values and release flags are in the separate expectation table. For these bounded cases there is exactly one candidate route per target; future multi-candidate ambiguity handling is outside this design.

Direct evidence anchors, in order: known-key verifier outcome; trusted-set membership decision; authoritative validity result; authoritative claimed-versus-expected epoch equality result; closed accepted-current same-subject/key/epoch competing-value result; presence of ten required accepted-current nonconflicting keys; native decision-visible guard; current authorized-path availability. Documented authorities VERIFIER, TRUST_REGISTRY, TIME_AUTHORITY, EPOCH_AUTHORITY, LEDGER_AUTHORITY, LEDGER_AUTHORITY, GUARD_AUTHORITY, COMMAND_AUTHORITY respectively. Their positive description is a declared **synthetic source specification**; the controlled test can falsify failure to discriminate stipulated meanings and contexts, not validate whether actual documentation or authorities tell the truth. The evaluator must not use a table of case IDs, literal per-case expected output, or the target field name as proof. Controlled-vocabulary/contract matching is admissible only if described as such, not a general semantic inference system.

For D_FRESH check three declared integer fields with same authoritative clock and scoped evidence, subject and decision, nonnegative issue/decision times, strictly positive duration, decision_time_s equals requested_context.decision_time_s. Then compare inclusive endpoints. For D_EPOCH require literal nonnegative integers and authoritative expected epoch, same context, expected_epoch equals requested_context.epoch. Python Boolean is not integer for this contract. Reject missing/invalid values with explicit status; no derivation on wrong clock/subject. These are the ONLY two candidate source-mapping derivations in this extension. S9 and S10 derivation registries stay empty. The inclusive boundary cases are static expected tests, not evaluated outputs.

### Ledger diagnostics are not new mapping derivations

C-03/04/05/06/07/08/09/11 supply a separate artificial complete or incomplete submitted-claim ledger. Diagnostic calculations do not confer source mapping DIRECT/DERIVABLE or add a ledger derivation to the registry. Each claim's signature and trust flags are stipulated synthetic premises; verify types and scope, compute fresh by the inclusive time rule and epoch equality, and accept only when signature/trust/fresh/epoch/sequence conditions all pass. Sequence > declared minimum; same source/epoch/sequence duplicate is an input integrity rejection in this extension (not a claim that this is exactly the historical verifier's output API). Check known source membership against supplied trusted set; reject inconsistent synthetic premises. Require literal Boolean claim values; historical Python equality semantics on non-Booleans are not tested or modified. In accepted claims retain maximum sequence per (source, subject, key, epoch); group by (subject,key,epoch), compare values, remove keys with competing values from current state. Ledger scope all keys for the same subject, epoch and instant. Contradiction true iff any such group conflicts. M_present iff every required key remains in current state; Q_satisfied iff each remains and its value is true. All-submitted aggregate flags are bool(rows) AND all rows satisfy the corresponding predicate, including rejected rows, not only accepted rows. Independent contact_available determines authorization_available. Incomplete inventory: null ledger-derived diagnostics even if the partial ledger seems adequate; independently known contact stays known; duplicate/invalid ledger: reject entire diagnostic instance with null fields, no downstream action. Reason priority for complete cases: required-key conflict, unrelated-key conflict, rejected extra row, missing required key, present-but-unsatisfied, then absent contact; reason must match the reference expected row. Security_signal is intentionally not derived from this ledger. Do not invoke a selector on a diagnostic that is not a complete eight-Boolean observation. No actual recovery-gate run or signature verification is part of this module.

## 2. M_present versus Q_satisfied — static source reconciliation

Frozen S9 semantic record: all ten criteria present in accepted state. Study 2 runtime_engine.py lines 163–166: all(criterion in current ...), where current_values removes contradictory keys. evidence.py lines 97–123: requirements_satisfied separately checks key and value equality. recovery_gate.py separately checks required values, contradiction and residual state. G3 g3_synthetic_parity.py lines 131–180 and 257: helper checks all expected values and the unexpected-value negative case sets minimum_evidence_complete=false. Therefore historical G3 passing 18 controls and 1,024 selector comparisons is real historical technical evidence, **not end-to-end equivalence of projection semantics**. The static discrepancy is confirmed, not a new failed run. No numeric S9/S10 mapping or non-evaluability change is justified: neither source audit admitted native state.

For the new protocol, M_present is the selector's frozen predicate; Q_satisfied is separate diagnostic. In a complete ledger with all ten accepted keys, no conflict and one false value (C-06), M=true, Q=false. Gate permission is a different proposition; a selector action to proceed to the gate does not grant recovery. A static illustration (not a measured output): with four evidence flags true, C=false, G=false, A=true, M=true, the pinned selector branches imply B0/S1 proceed to gate and B1/B2 preserve limited operation. Substituting Q=false into M would instead imply B0 restrict, B1 preserve, B2 hold, S1 hold. This follows by reading the code, not executing it; the gate would still reject unsatisfied required criteria. No new performance or correctness result. Preserve the historical G3 case and report that its helper modeled satisfaction as completeness; do not retroactively alter the old test or pass receipt.

## 3. F0/F1/F2: exact conditional logical domains and counterexamples

Use x=(S,T,F,E,C,M,G,A) in frozen predicate order. Let R be the ten named required keys. F0 is the full Boolean cube. F1 = {x in F0: M implies not C}. Its architecture assumption is a complete submitted snapshot restricted to R, one subject, one expected epoch and one decision instant; contradiction covers that same required-key scope. If C holds, a conflicting required key is removed from current_values, so M is false. Hence M implies not C. It is not valid for a ledger containing unrelated keys/subjects; C-08 supplies ten consistent required keys and a conflicting unrelated key. That case is allowed by F0 but violates the F1 implication if improperly treated as a required-only ledger. C-07 supplies the required-key conflict and M=false, C=true. A ten-key nonconflicting ledger (C-06) is a nonempty witness for F1 even with a false value.

F2 = {x in F1: M implies (S and T and F and E)}. Additional named conditional architecture guarantee: when M=true, the **entire submitted snapshot**, not a post hoc filtered subset, is nonempty and every submitted row is accepted. The acceptance conjunction includes the four evidence flags (and sequence validity); each all-submitted aggregate flag is therefore true. This is a hypothetical complete-snapshot publication contract, not a property of the general runtime. No rejected row may be hidden to force the implication. C-09 has all ten required accepted keys plus a rejected extra row with signature failure; the general all-submitted signature aggregate is false while M=true. That is a counterexample to imposing the implication on the unrestricted runtime. C-06 (and C-11 with contact unavailable) has a complete nonconflicting accepted snapshot and witnesses nonemptiness of F2. C-11 also refutes M or Q implying A; C-06 refutes M implying Q. Guard G and path availability A are unconstrained. The constraints are logical **outer approximations** under named hypotheses; not every permitted tuple has been shown to arise from a concrete ledger, let alone from a mission. No claim of physical feasibility, independent interface necessity, or conformance to a standard.

Static combinatorial check (derived on paper, not enumerated results): F0 has 2^8=256; F1 permits 2^7 assignments with M=false and 2^6 with M=true,C=false, totaling 192. F2 permits the same 2^7 M=false assignments and four assignments when M=true,C=false and the four verification predicates are true (G,A free), totaling 132. These are prereview algebraic expectations for the proposed definitions, not measured counts. F2 subset F1 subset F0; the new study must test its implementation against these fixed predictions, not select a model based on a favorable sidecar result.

For o in {null,false,true}^8 define U(o) as unknown coordinates and X(F,o)={x in F matching every known coordinate}. Empty X => INCONSISTENT_OBSERVATION; no actions, cardinality or sidecar minimum reported. Nonempty X and frozen selector f_p: action set = f_p(X). For each S subset U(o), partition X by projection onto S. S sufficient iff each nonempty partition cell has a singleton action image. Unattainable assignments skipped, not successes. Retain all minimum-cardinality sets, including empty S iff action already unique. A finite nonempty X has a sufficient S=U(o) because fully revealed completions are unique. For nested X' subset X with both nonempty, f_p(X') subset f_p(X), and a sufficient S for X remains sufficient for X' since each new nonempty cell is contained in an old cell. Thus min size cannot increase. Compare common feasible slices, same o and semantics; no monotonic claim across nonnested models or different observations. Strict reduction not required. No sidecar calculation or new selector enumeration performed.

## 4. Independent technical oracle and implementation plan

Future reference implementation and candidate evaluator are separately authored and reviewed, with no import of each other's semantic decision logic. Reference A: static expectation table + independent manual/spec interpretation of exact synthetic semantics; one-to-one compare all 72 expected rows, including 8 diagnostics. Candidate evaluator sees only input; runner joins on opaque IDs afterward. Keep gold file outside evaluator's allowed read paths, pinned before implementation, no case-specific branches or expectation-file imports. Authorship is shared and public design is visible: this is technical separation, **not a blinded test set** or independent personnel adjudication. Implement independent ledger diagnostic using group-by and set operations; candidate may use explicit iteration, but no shared rule-evaluation or parsing routine for their scientific logic. Both adhere to the same declared semantics; expected classifications remain author-reviewable.

Reference B: separate Boolean policy oracle from source branches: q=S and T and F and E and not C and M. B0 restrict iff not q else proceed; B1 restrict iff q and G else preserve; B2 hold iff not q, else restrict iff G else preserve; S1 hold iff not q, else restrict iff G and not A else proceed. No selector imports in oracle; harness compares all complete-state actions to pinned selector as technical regression (not novel finding). Candidate sidecar algorithm enumerates partitions. Independent oracle uses conflicts: for every x,y in X with unequal action, S must intersect their differing unknown-coordinate set. Proof: a disjoint S leaves same S projection and different actions, violating sufficiency; intersecting every conflict pair prevents this. Enumerate subsets in lexicographic frozen-coordinate order, preserve all minima, compare exact sets not just cardinalities. Reduce redundant conflict masks if needed, with proof and regression checks. Full all-unknown first, then all 3^8 partial patterns, four policies, all three models; no data-dependent exclusions. Cache completion masks and policy labels; finite eight-variable problem, no measured runtime claimed. This is a genuinely different sidecar checker, not an alias of the candidate partition function.

Baseline rules fixed in candidate manifest: always unknown; exact name-only matching with literal Boolean row value, no semantics/scope/derivation. They are intentionally simple diagnostic comparators, not state-of-art methods. Evaluate class/admission/value only on 64 mapping cases, not ledger diagnostics. Count false admission = admitted where expected nonadmissible / 41; false rejection = nonadmission where expected admissible / 23. Wrong admitted Boolean separately counted. Full per-family confusion matrix; reason/rule/release/status exact matches for candidate, not simplistic baselines. Count known false -> unknown and unknown -> false separately. Ledger diagnostics exact field comparisons, including null. No pooled statistical inference. Report all mismatches and baselines, including if candidate fails; no strict superiority claim.

Metamorphic checks fixed at 17: eight D_TRUE direct field renames with corresponding value-key renames; eight D_FALSE cases add unrelated integer field/counter then compare both orderings against base; one offline-only label flip. Reference unchanged class/admission/value. Apply transformations exactly as manifest states, not new independent cases; no leakage of case ID or target-bearing field name into semantic inference. Negative mutation tests planned: substitute CRC for signature, treat false as absent, use offline label, ignore wrong clock, accept nonpositive interval, substitute Q for M, discard unrelated contradiction, silently discard rejected rows, return sidecar zero on empty X, alter one policy branch, use non-nested models as nested. Each must be caught by corresponding reference or invariant. Mutations are implementation validation only and never written into frozen original code.

## 5. Freeze and execution holds

The candidate JSON and this document are exact **design artifacts**, not run inputs. Before any execution: author approves the immutable protocol payload; separately authorize implementation/materialization with exact runtime fixtures and hashes, code review, pinned source/code/input digests and network-disabled runtime; then separately approve execution. Record design exposure and no external preregistration. No fixtures generated by an experimental harness, no policy/selector run, no original dataset accessed, no raw publication. A future runtime generator must reproduce input specification without reading expected values, reject unknown keys or malformed types, produce stable UTF-8 LF sorted JSON, hash every input/reference/output with SHA-256 and preserve failures. Version pin original sources; if future implementation uses original code, ensure byte-identical read-only dependency, never modify historical studies. A final design review cannot make an empirical claim or clear author rights. Stop at any pin, scope, input or oracle mismatch, or failure of invariant; retain complete failure artifacts and obtain approval for documented changes. No post-result adjustment of model or fixtures.

**Static design conclusion:** detailed specifications are suitable for author review of a prospective freeze candidate, contingent on review/approval and exact payload pinning. They do not establish independent operational construct validity, actual mission feasibility, broader semantic-transition results, or journal significance.
