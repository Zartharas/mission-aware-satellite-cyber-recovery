## Why Limit Checker is a suitable aerospace fixture

NASA's LC description states that LC monitors telemetry data points, compares them against predefined threshold limits, issues event messages when threshold conditions are encountered, and may initiate a Relative Time Sequence response.

This gives S6X a concrete aerospace-software semantic property rather than a generic toy program.

The design remains an artifact-assurance experiment. It does not evaluate operational fault-management performance.

## Requirement-bound semantic invariant

NASA LC requirement `LC2003` requires data to be compared with the table-defined comparison value and operator.

Requirement `LC2003.1` explicitly requires support for:

- `=`
- `!=`
- `>`
- `>=`
- `<`
- `<=`

At the pinned LC commit, `LC_SignedCompare()` implements:

- `LC_OPER_GT` as `WPValue > CompareValue`
- `LC_OPER_GE` as `WPValue >= CompareValue`

### Primary invariant family: signed integer GT/GE boundary

For comparison value `0`:

| Operator | WP value -1 | WP value 0 | WP value +1 |
|---|---|---|---|
| `GT` | FALSE | **FALSE** | TRUE |
| `GE` | FALSE | **TRUE** | TRUE |

The equality boundary is the discriminating case.

### Independent adjudication rule

The research-only correctness adjudicator will require exact agreement with the frozen truth table above.

The adjudicator must run outside the qualification gate and must not contribute to any of the six Study-6-aligned assurance signals.

## Important upstream-test observation

At the pinned LC commit, the direct upstream tests:

- `LC_SignedCompare_Test_GT`
- `LC_SignedCompare_Test_GE`

both use `WPValue=1` and `CompareValue=0`.

Therefore those direct tests verify positive cases but do not exercise the `WPValue == CompareValue` boundary that distinguishes `>` from `>=`.

This does **not** prove that the complete upstream cFS/LC test suite would miss the proposed semantic fixture. That question remains empirical and cannot be reported until a separately authorized implementation stage.

## Prospective artifact states

### CLEAN_APPROVED

Pinned unmodified source, valid build, all six assurance signals true, invariant expected to pass.

### POST_RELEASE_TAMPER

Post-build byte modification after release/signature binding. Expected assurance differences must be generated by the future implementation, not hard-coded as results.

### TRUSTED_SIGNER_VARIANT

Research-controlled altered artifact signed with a designated research signing identity while independent target/provenance evidence should expose the mismatch.

### TRUSTED_BUILDER_VARIANT

Research-controlled build-stage divergence with valid signature/target digest but independent rebuild evidence intended to expose the divergence.

### SOURCE_REVIEW_BYPASS

Reproducible artifact with review attestation intentionally absent.

### APPROVED_BAD_SOURCE

`S6X_FIXTURE_GT_EQ_BOUNDARY_001` built reproducibly from the pinned but intentionally altered source, with all six process-assurance signals prospectively capable of being true while the external functional invariant fails.

The final state is the direct executable instantiation of Study 6's observational-equivalence question.

## Research-only signing and attestation rules

If implementation is later authorized:

- generate ephemeral research-only signing keys;
- never use NASA, mission, production, or third-party credentials;
- clearly label review and approval attestations as experimental metadata;
- bind every attestation to source commit/fixture ID and artifact digest;
- independent rebuild must occur from a separately instantiated build directory/environment;
- do not use the functional adjudicator in build approval or gate logic.

## Minimum implementation matrix if later authorized

The first implementation should remain narrow:

- source identities: baseline + one approved-bad-source fixture;
- comparison datatype: signed 32-bit integer only;
- invariant inputs: `-1, 0, +1` against compare value `0`;
- gates: the existing six Study-6 gate definitions;
- artifact states: only those needed to instantiate the frozen Study-6 categories.

Unsigned and floating-point variants are reserved for robustness only and should not be added unless the primary invariant behaves as designed.
