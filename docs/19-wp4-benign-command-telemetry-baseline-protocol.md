# WP4 Gate 3B Phase 2 — Benign Command and Telemetry Baseline Protocol

## Purpose

This protocol defines the deterministic, non-adversarial command-and-telemetry test that must pass twice from clean runtime state before any event-injection implementation begins.

The protocol extends the accepted Phase 1 runtime topology. It does not add COSMOS, publish host ports, use live RF, contact external systems, or enable event injection.

## Selected benign command

The selected command is the pinned NOS3 sample application's no-operation command:

- command name: `SAMPLE_NOOP_CC`;
- command message ID: `0x18FA`;
- command function code: `0`;
- command arguments: none;
- command packet length field: `1`;
- housekeeping telemetry message ID: `0x08FA`.

The command is selected because the pinned NOS3 source includes an upstream system test that already defines a narrow acceptance pattern: capture initial sample housekeeping counters, issue `SAMPLE_NOOP_CC`, require the command counter to increase, and require both the command-error and device-error counters to remain unchanged.

## Frozen transport path

The Phase 2 ground probe will remain a container on the project internal Docker bridge. It will not publish ports.

### Telecommand path

1. The ground probe sends one plaintext cFS command packet by UDP to `cryptolib:6010`.
2. CryptoLib applies the pinned telecommand framing and security processing.
3. CryptoLib forwards the processed telecommand by TCP to `radio-sim:8010`.
4. The radio forwards the command toward cFS on the configured flight-software command path.

### Telemetry path

1. cFS emits telemetry through the configured flight-software telemetry path.
2. The radio forwards telemetry by TCP to `cryptolib:8011`.
3. CryptoLib processes the telemetry frame and forwards plaintext space packets by UDP to `ground-probe:6011`.

For Phase 2, CryptoLib must use `GSWALIAS=ground-probe`; the Phase 1 loopback value is not acceptable because it cannot provide independently captured ground evidence.

## Ground-probe startup order

1. Start the internal ground-probe container and bind UDP port 6011.
2. Start NOS Engine, the time driver, headless 42, and the byte-count-only truth sink.
3. Start the frozen hardware simulator set and wait for the radio TCP listener on port 8010.
4. Start CryptoLib with TCP enabled, `CRYPTO_HOST=0.0.0.0`, and `GSWALIAS=ground-probe`.
5. Confirm radio/CryptoLib transport establishment.
6. Start cFS and the dedicated command-bus bridge.
7. Observe sample housekeeping telemetry before sending any command.

A ground-probe DNS or socket-readiness failure is `RUN_INVALID`, not a command failure.

## Command packet contract

The command packet must be generated deterministically from the pinned command definition and recorded before transmission.

Expected fields:

| Field | Value |
|---|---|
| CCSDS stream ID | `0x18FA` |
| CCSDS sequence control | `0xC000` for the initial baseline packet |
| CCSDS length | `0x0001` |
| Function code | `0x00` |
| Checksum | Generated by the pinned cFS-compatible checksum routine |
| Arguments | None |

The runner must verify its generated packet against the pinned field values before transmission. A packet-construction or checksum self-test failure is `RUN_INVALID`.

Exactly one `SAMPLE_NOOP_CC` packet may be transmitted in each accepted baseline run.

## Pre-command telemetry readiness

Before command transmission, the ground probe must receive at least two valid `SAMPLE_HK_TLM` packets with message ID `0x08FA`.

The two most recent pre-command packets must show stable values for:

- `CMD_COUNT`;
- `CMD_ERR_COUNT`;
- `DEVICE_ERR_COUNT`.

Any unexplained counter change before the test command indicates background command activity or parser ambiguity and results in `RUN_INVALID`.

The last stable pre-command packet establishes:

- `cmd_count_before`;
- `cmd_err_count_before`;
- `device_err_count_before`;
- `pre_command_packet_sha256`;
- `pre_command_received_utc` and monotonic timestamp.

## Deterministic acceptance assertion

Within 30 seconds after the recorded command-send time, the ground probe must receive a valid `SAMPLE_HK_TLM` packet satisfying all three conditions:

1. `CMD_COUNT == (cmd_count_before + 1) mod 256`;
2. `CMD_ERR_COUNT == cmd_err_count_before`;
3. `DEVICE_ERR_COUNT == device_err_count_before`.

The first telemetry packet satisfying all three conditions is the accepted post-command packet.

The runner must record:

- `command_sent_utc` and monotonic timestamp;
- transmitted packet length and SHA-256;
- `post_command_received_utc` and monotonic timestamp;
- post-command packet length and SHA-256;
- parsed before and after counter values;
- measured command-to-acceptance latency.

## Failure classification

### `BENIGN_BASELINE_PASS`

All infrastructure, isolation, packet-construction, pre-command stability, command transmission, and post-command assertions pass.

### `BENIGN_BASELINE_FAIL`

The runtime and transport remain healthy, but the correctly constructed command does not produce the required counter transition within 30 seconds, or an error counter increases.

### `RUN_INVALID`

Examples include:

- any required container exits;
- the ground probe cannot bind or resolve its internal endpoint;
- telemetry parsing is ambiguous;
- no stable pre-command housekeeping baseline is available;
- multiple commands are transmitted;
- packet construction or checksum self-validation fails;
- the internal-network, no-host-port, or no-Docker-socket constraints fail;
- evidence capture or cleanup is incomplete.

## Evidence separation

Each run must create two distinct evidence products.

### Immutable ground evidence

This path may contain:

- raw transmitted and received packet bytes;
- packet hashes and lengths;
- UTC and monotonic timestamps;
- complete before/after parsed fields;
- container liveness, inspect, network, and cleanup evidence;
- the byte-count-only 42 truth-sink status;
- runner assertions and terminal classification.

This evidence is evaluation-only and must not be mounted into or otherwise exposed to later policy containers.

### Policy-visible evidence

This path may contain only the telemetry fields and contact-state information that a response policy would legitimately observe. It must exclude:

- truth-sink bytes or status beyond declared contact availability;
- raw Docker inspection data;
- host or orchestration state;
- future event labels or injection timestamps;
- evaluation-only packet annotations.

Both evidence products must be hashed independently.

## Two-run acceptance gate

The complete baseline must pass twice from clean runtime state using different run IDs.

For each run:

1. verify no project-labeled resources exist;
2. launch from the frozen commits, image digest, and build lock;
3. transmit exactly one benign command;
4. satisfy the deterministic telemetry assertion;
5. complete evidence hashing and project-scoped cleanup;
6. retain a compact committed run lock while keeping large logs ignored.

After both passes, compare:

- component count and identities;
- command packet bytes and hash;
- pre/post counter transitions;
- command-to-acceptance latency;
- telemetry packet identities and lengths;
- isolation and cleanup results.

Unexplained structural variation blocks the gate even when both individual runs report pass.

## Safety boundary

This protocol contains no cyber event, malformed packet, replay, unauthorized command, RF activity, credential use, scanning, interception, or operational target. Event injection remains disabled until both baseline runs pass and evidence separation is verified.
